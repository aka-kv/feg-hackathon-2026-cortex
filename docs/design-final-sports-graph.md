### Phase D addendum — write-time caching, requested demo flow, 10-case QA

**Ask**: recommendations must be ready the instant a user returns to the home screen, not computed on that request — and this must hold for a brand-new anonymous user, a returning user with minimal history, and a returning user with heavy history, all at effectively O(1) read latency.

**Design**: moved computation from read-time to write-time. `POST /v1/events` now calls `rank.recommend()` immediately after updating session state and caches the result on the `SessionState` object (`session_store.py`). `GET /v1/recommend/cached/{session_key}` is then a single dict lookup — no graph traversal, no ranking, on that request. Added `POST /v1/login` (demo convenience) that seeds a new session with a real returning player's own recent real fixtures (pulled from the raw event log, never fabricated), so a heavy-history user can already be past the trigger the instant they log in.

**Measured, not asserted** (all sub-millisecond, live against the running server):
- Login (new/anonymous): 0.335 ms
- Login (minimal, 1 seeded fixture): 0.201 ms
- Login (heavy, 4 seeded fixtures, already past trigger): 0.04 ms
- Per-click write (recompute + cache): 0.04–0.26 ms, stable across 20 rapid clicks up to 20 distinct fixtures (mean 0.135 ms, no degradation observed)
- Home-page cached read: 0.003–0.02 ms

**Precision on the "O(1)" claim**: not literally O(1) in the mathematical sense — the write-path cost is O(k) in the number of distinct fixtures a *session* has accumulated (each requires a dict lookup + a small merge/sort), and the read-path is a genuine O(1) dict lookup. For any realistic session size this is sub-millisecond regardless, but "effectively constant time in practice for bounded k" is the honest claim, not "mathematically O(1)."

**10-case adversarial QA, executed live, not reasoned about:**
1. Login with an unknown `player_id` → clean 404, no crash.
2. Cached read for a session_key that was never created → clean `no_session_or_expired`, no crash.
3. Three repeated clicks on the identical fixture → `distinct_fixtures_seen` stays at 1 (no false inflation).
4. Two different session_keys clicked independently → zero cross-contamination confirmed.
5. Protection state flips allowed → self_excluded → allowed mid-session → cache correctly reflects the current state at each step, and correctly resumes with all accumulated history (including fixtures viewed while blocked) once re-allowed.
6. 20 rapid successive clicks → timing stayed flat (~0.13ms mean), no degradation.
7. Malformed request (missing required field) → clean 422 from Pydantic validation, no crash.
8. Debug endpoint (`GET /v1/sessions/{key}`) → node/fixture counts exactly match what was posted.
9. Health endpoint → active session count accurate after all test traffic.
10. TTL expiry → verified directly against `SessionStore` with a 1s TTL: after expiry, both `get_recent_nodes` and `get_cached_recommendation` correctly return empty/None, and the expired entry is purged from memory on that read.

**Known limitations, stated plainly rather than discovered later:**
- The in-memory `SessionStore` dict is not lock-protected — fine for a single-presenter demo, a real race risk under genuine concurrent load on the same session_key (not expected here, but not fixed either).
- `/v1/login`'s real-history seeding loads and groups the *entire* raw event log into memory at startup — a reasonable demo convenience at this sample's scale (92 players, 1.4M rows), explicitly NOT the production design; a real system would look up a returning user's recent activity from a proper per-user store, not scan a full raw log.
- The heavy-history login scenario uses the all-data serving artifacts (a real system recognizing a real returning user's own pattern — legitimate), which is a **different claim** from the held-out 42.1%-vs-3.5% generalization metric (Phase C) and must never be conflated with it in the pitch: one demonstrates recognition of a known user, the other demonstrates generalization to unseen sessions.

**Before declaring this done, ran the exact planned live-demo sequence end-to-end** (login → check Home *before* any clicks → click 3 real target fixtures → check Home again) rather than just smoke-testing each endpoint in isolation — and it caught a real, serious bug: **step 2 (Home immediately after login, zero fixtures opened yet) returned "no session," not the cold-start popularity picks.**

Root cause, traced precisely: `SessionStore` only ever created a session entry inside `add_nodes()`. A deliberately-unseeded login (exactly what the live demo needs — every fixture "open" should be a real, on-screen click, not invisible pre-seeded state) never calls `add_nodes()` with anything, so the session was never created at all; `set_cached_recommendation()` then silently no-op'd against a session key that didn't exist. Compounding this, `get_cached_recommendation()`'s `if not nodes: return None` treated "valid session, zero fixtures yet" identically to "no session" — a legitimate cold-start state was indistinguishable from an error state.

**Fixed**: added `SessionStore.ensure_session()`, which creates the session entry independent of whether any nodes are being added, called explicitly at the start of all three login endpoints (`/v1/login`, `/v1/auth/login`, `/v1/login-verified`) before the write-time cache runs. `get_cached_recommendation()` now checks session validity (exists, not expired) directly, never infers it from node count. Re-ran the exact sequence after the fix and confirmed all three cases correctly: fresh login → valid cold-start picks immediately; 3 real clicks → correct personalized prediction; new/guest account → cold-start picks immediately too.

**Demo accounts** (`_DEMO_ACCOUNTS` in `app.py`): `marko89`/`psk2026` — real, held-out, verified session `1785708852`, started with zero pre-seeded history so all 3 fixture-opens happen live on screen; `newplayer`/`psk2026` — genuine cold start, no target sequence. `marko89`'s 3 target fixtures are pinned to the front of the Football page's fixture list for reliable, repeatable live demos: open (in order) the 1st, 2nd, and 3rd fixture cards shown, then go to Home — the top pick will be the fixture this real historical person actually went on to bet on next, verified three separate ways already (held-out evaluation, raw-file Excel proof, live API replay).

### Phase E addendum — real bugs found by actually clicking through, and a `rank.py` hardening pass

The user clicking through the restyled frontend found two real, distinct bugs — worth recording precisely, not just "fixed some things":

1. **Illustrative-name collisions.** The team-name generator *hashed* each real `fixture_id` into a name from a 10-team pool (~90 possible pairs). With more than a handful of fixtures shown, two completely different real fixtures could collide onto the identical displayed name — looking exactly like "the same match recommended twice" when the underlying fixture IDs and the recommendation logic were actually correct (verified separately). Fixed by assigning names deterministically and uniquely instead of hashing: first fixture ID seen gets pool-name #0, second gets #1, etc. (`fixtureNameAssignments` Map, 132-name pool from a 12-team roster) — zero collisions possible below 132 distinct fixtures shown in one session, with an explicit warning surfaced if that's ever exceeded rather than silently repeating.
2. **Non-deterministic tie-breaking in `rank.py`, found while investigating (1).** `graph_candidates()` iterated a Python `set` (hash-order dependent, can vary across process restarts under hash randomization) and `popularity.py`'s sort used pandas' default non-stable algorithm — meaning two equally-scored fixtures could silently swap which one "wins" a tie between runs. **Fixed with explicit secondary sort keys everywhere a tie is possible**: `graph_candidates` now sorts `seen_fixtures` before iterating and ranks by `(score desc, fixture_id asc)`; `popularity.py` now sorts by fixture ID first, then a stable (`kind="mergesort"`) sort by `bet_intent_count`. Added two runtime assertions in `recommend()` as a permanent regression guard: no duplicate fixture in the returned candidates, and no candidate that the session already opened.
3. **Consequence, confirmed not assumed**: re-running the full held-out evaluation after the fix moved the headline number from 42.3% to **42.1%** (previously-arbitrary ties now resolve consistently) and **changed which 2 of the 10 "verified genuine hit" demo sessions are actually still hits** — `1785590038` and `1785672096` dropped out (were hits only by winning a since-fixed non-deterministic tie), replaced by `1785708852` and `1785756954`. Directly checked `1785672096` against the corrected code and confirmed it is now a genuine miss, not a hit — regenerated `ten_users_source_of_truth.{xlsx,json}`, `session_proof_minimal.xlsx` (now `1785708852`), and `docs/mentor-briefing-three-users.md`'s Scenario 2 accordingly. This is exactly why the assertions in point 2 exist: a future change that reintroduces this class of bug should fail loudly during development, not get discovered live in front of a mentor.
4. **Other frontend fixes, per explicit request**: removed the mascot entirely (plain numbered rank badges instead, all three pick-cards visually identical); removed the "Why this?" button and its `alert()` popup (a real, valid complaint that native browser alerts look like an unfinished demo, not a product); replaced the fake `demo01`–`demo05` placeholder fixture IDs with a new `GET /v1/browse-fixtures` endpoint serving real fixture IDs from the popularity artifact, so every clickable fixture on the page is now real, not invented; wired the previously-dead "Place demo bet" button to actually post real `betslip_placed_bet` events for the slip's contents (audited every `<button>` element on the page against this — the other four are all genuinely wired: 2 login buttons, 3 odds buttons per fixture); odds buttons (1/X/2) now visibly select per-button (was previously indistinguishable, all three did the identical thing) and populate an explicit `betSlip` JS array instead of ad-hoc DOM text parsing (the likely root cause of the very "undefined" symptom that led to finding bug #1).

## 0. What changed, and why

Mentor feedback after round 1: **narrow to sportsbook only, drop casino**, and reframe around a concrete, provable mechanism — map every in-session interaction into a graph, and use it to predict what an anonymous, in-progress session is likely to do next (specifically: which fixture they're likely to bet on), surfacing that prediction as a soft, non-pushy "top picks" nudge. The mentor's explicit test: **is this scalable to billions of events, and do we even need AI/ML to do it.** This document answers both questions and fixes the build's scope before any code is written.

## 1. Scope

**In scope:** sportsbook only — browsing, comparing fixtures, building a bet slip, placing a bet. Everything is scoped around `top_sport_users_event_logs.csv`, `SB_Player.csv`, `SB_MOM.csv`, `EPS_Offers.csv`, and `hackathon_sportsbook_trends.xlsx`.

**Out of scope:** casino entirely (drop `CA_Player.csv`, `CA_MOM.csv`, `top_casino_users_event_logs*.csv` from this build). The near-miss-chasing branch, the four/six-way hesitation classifier, and the casino deposit/bonus confirm-step framing from the earlier docs are all dropped with it.

**Also explicitly not doing:** using location or other personal data to enrich the graph. See §5.

## 2. The problem, restated precisely

An anonymous (or pseudonymous) in-progress session generates a stream of interaction events. As the session accumulates events, predict what it's likely to do next — specifically, which fixture it's likely to place a bet on — and surface that as a passive "you might like this" recommendation once the session shows enough signal (mentor's example: after ~3 fixtures viewed). This is **session-based next-item recommendation**, a well-studied problem (item-to-item collaborative filtering, session graphs / SR-GNN, sequence models like GRU4Rec) — we are not inventing the category, we're applying a known-scalable pattern to this specific data and this specific compliance context.

## 3.6 Data cleaning rules for Phase B (derived from a full cleanliness audit, every rule backed by a direct query — see §10 entries 14–18)

**These are not optional polish — the graph will be structurally wrong without them.**

1. **Session key must be `(session, PlayerID)`, never `session` alone.** Confirmed: 68 of 16,156 `session` values (0.42%) are shared by two different `PlayerID`s, and manual inspection of one showed genuinely time-interleaved events from both players (both active in the same minute) — not sequential ID reuse. Root cause: `session` behaves like a second-granularity epoch timestamp of session start (e.g. `1785566256` ≈ 2026-08-01 06:37 UTC), which is inherently collision-prone at scale. Splitting only by `session` would splice two different people's walks into one graph path.
2. **Android `screen_view` events need an explicit fallback node, not a drop.** 59.4% of `screen_view` rows (Android-only event type, distinct from iOS's `fortuna_screen_view`) have every field blank except `event_name`/`session`/`timestamp`/`platform`/`PlayerID` — no `fortuna_screen_name`, no page/route info, nothing. That's ~189,600 rows, ~13.6% of the entire file. Map these to an explicit `unknown_screen(platform=Android)` interaction node. Dropping them instead would make Android sessions look artificially sparser than iOS sessions for no real behavioral reason — a platform bias baked into the graph by omission.
3. **`betslip_add_bet` rows missing `fixture_id` (56,541 of 185,331, 30.5%) are a real, well-defined action type, not broken data.** All 56,541 are `platform=SB iOS`; 56,004 of those are specifically `added_from=betslip_history` (re-adding a bet from betslip history) and 100% of that subset also lack `selection_id`/`betslip_number` — the fixture context is implied by the referenced historical ticket, not re-emitted by this event. Model `betslip_add_bet(added_from=betslip_history)` as its own interaction node ("repeat-from-history"); do not force it into a fixture-content edge it doesn't carry.
4. **Content-node ID pattern must be widened**: not just `ufo:mtch:` (individual match fixtures). 52 `fixture_id` values that looked "malformed" against that pattern are actually valid alternate content types — `ufo:race:` (horse/greyhound racing) and `ufo:otrt:` (outright/tournament-winner markets). Match on `ufo:(mtch|race|otrt):` and treat race/outright as legitimate additional content-node subtypes.
5. **78 timestamps (0.006% of rows) fail to parse** under the standard parser — coarser-grained strings missing fractional seconds (e.g. `2026-08-14 18:05:33 UTC`). Quarantine and count these explicitly if a fallback parse also fails; never silently drop them from a session's edge sequence.
7. **Casino exclusion must also filter `page_view` rows by `page_location` domain, not just `event_name`.** 7,351 `page_view` rows (5.6% of all `page_view`s) point to `casino.psk.hr` — drop these too (see §3.1 correction). For the remaining 124,050 legitimate sportsbook/account `page_view` rows (all on `www.psk.hr`/`account.psk.hr`/`bonus.psk.hr`), extract a node from the URL path with query-string tokens stripped (e.g. `/oklade/tenis`, `/user/betslips`, `/my-account/deposit`, `/bonus/<offer>`) — don't discard these as "no node identity," they're genuine and informative.
8. **Confirmed clean, no action needed:** zero exact-duplicate rows in this file (unlike the casino v1/v2 files' duplicate issue noted elsewhere); no session spans beyond 16.0 hours (no cross-day session bleed — safe to treat each session as one bounded temporal walk); `PlayerID` is always a well-formed 64-character hash with zero blank values.

## 3.7 Sport segmentation — fixing "won't the same popular fixture get recommended to everyone?"

A fair, sharp question to anticipate from a mentor: a co-occurrence graph built from aggregate historical counts can end up dominated by whatever is generally popular, regardless of who's asking — the same failure mode as a plain popularity list, just hidden behind a graph. Tested this directly rather than assuming either way:

**The problem was real, measured concretely.** Before any fix: across 776 held-out test sessions, one football (`nogomet`) fixture was the #1 recommendation for 53 of them — but only 11 of those 53 sessions were even watching football. The other 42 were tennis, e-basketball, baseball, e-hockey, esports sessions, getting a real football match recommended purely because it was globally popular, not because it was relevant to them.

**First fix attempted and rejected**: PMI/"lift" normalization (divide each edge's co-occurrence count by the target fixture's overall popularity — the standard fix for popularity bias in the recommender-systems literature). Tested against the same held-out evaluation: it only marginally improved diversity (top-1 share of all rank-1 picks: 6.8% → 6.4%) while cutting hit rate nearly in half (41.6% → 26.4%). Reason: co-occurrence counts here are sparse (median 2 per pair — see §3.1), so dividing by popularity mostly amplifies noise from rare, low-confidence pairs rather than surfacing genuine under-appreciated affinities. Rejected, not adopted, because it was tested and found wanting for this specific data's sparsity — not assumed to be the answer just because it's the standard technique.

**Fix adopted: sport segmentation** (`sport_segmentation.py`) — restrict candidates to the same sport(s) the session has already shown interest in, using the `sport_name` field already in the data (99.7% of fixtures have a reliable sport mapping, built via mode over all rows for that `fixture_id`; the mapping is built from the **full dataset, not train-only** — a fixture's sport is static match metadata, not a behavioral signal, so using the full dataset doesn't leak anything about a held-out session's future actions, unlike the co-occurrence counts, which must stay train-only). Not a clustering algorithm — a real, existing category already in the data, which is why it costs nothing in accuracy and stays fully explainable.

**Result, measured on the same held-out evaluation, via the actual production `rank.py` code path (not a side test script):**

| | Before (unsegmented) | After (sport-segmented) |
|---|---|---|
| Hit rate@3 | 41.6% | **42.1%** (no cost — slightly better) |
| Cross-sport violations | 53 sessions affected | **0** |
| Top-1 fixture's share of all rank-1 picks | 6.8% | **2.2%** |
| Top-3 fixtures' share | 9.7% | 6.1% |
| Top-10 fixtures' share | 15.9% | 13.4% |
| Distinct fixtures ever recommended as #1 | 462 | 461 |

This is now the production configuration — wired through `rank.py` (`sport_map` parameter, applied to both the graph-candidate and popularity-backfill paths), persisted as `artifacts/fixture_sport_map.json` (built in `build_artifacts.py`), and loaded by the live API (`app.py`, `_sport_map`). Both mentor-briefing example sessions (`1785672096` minimal, `1785590016` heavy) were re-verified and still hit correctly under this change — re-generated their proof files rather than assuming the change didn't affect them.

## 4. Graph schema

**Two node types (heterogeneous graph), not one:**

1. **Interaction nodes** — the 56 verified `fortuna_screen_name` values + the action event types. Small, fixed cardinality. Doesn't grow with data volume.
2. **Content nodes** — fixtures (16,693 distinct in the sample; bounded in production to whatever matches are currently live/upcoming, since concluded fixtures age out — this layer is naturally self-pruning). Optionally, a finer layer of selections (44,905 distinct) if fixture-level granularity proves too coarse.

**Edges** = every observed transition between two nodes, in temporal order, within a session, carrying context attributes where available: `added_from`, `status`, `betslip_type`, `platform`.

**Example real session walk** (this is what actually gets graphified, not "viewed game X"):
`homepage → prematchSports → prematchDetail(fixture A) → prematchDetail(fixture B) → prematchDetail(fixture C) → betslip_add_bet(fixture C, added_from=match_detail_odds) → betslip → betslip_placed(betslip_type=SOLO) → betslip_placed_bet(fixture C, status=ACCEPTED)`

## 6. Algorithm and architecture

**Two-stage, same shape regardless of how many signals get added:**

1. **Offline (batch — this is where the billions of events go, never in the live path).** A Spark/Flink job scans historical sessions and counts transitions between node-pairs (screen→screen, screen→fixture, fixture→fixture, fixture→outcome), optionally sliced by a *small* number of context dimensions (platform, time-bucket, betslip_type — not every signal at once, to avoid sparse, useless slices). Keeps top-K next-nodes per node per slice. Refreshed on a schedule (nightly batch, or incrementally via streaming aggregation).
2. **Online (serving — touches almost nothing, regardless of history size).** The precomputed graph is compacted into a fast key-value index (Redis/DynamoDB): node → ranked next-nodes. An active session holds a short list of recently-visited nodes; at decision time (mentor's example: after 3 fixtures viewed), a handful of O(1) lookups merge into a candidate list.
3. **Ranking layer (the one place a small model earns its keep).** Once candidates come back from the graph, a lightweight, explainable model (logistic regression or small GBM — not deep learning) re-ranks them using the richer context signals from §5: popularity prior (cold start), recency/proximity-to-kickoff, platform, and — once the production ID-mapping dependency in §3.4 is resolved — odds context. Every feature is named and inspectable; no black box.
4. **Cold start resolution, explicitly**: for a brand-new anonymous session with fewer than 3 fixture-views, recommendations fall back entirely to the `SB_MOM.csv`-derived population popularity prior. Once the session accumulates its own graph signal, the session-specific candidates take over.

**Why not deep learning (SR-GNN, GRU4Rec, etc.)**: no reliable labels exist to validate a learned model against; a trained model would be less explainable for the exact same outcome; and the compute cost is unjustified when count-based aggregation already solves the scalability question. This is a considered choice, not a shortcut — say so if asked.

## 7. Compliance overlay (carried forward, still binding)

- The recommendation candidate — however it's generated — passes through a **protection/eligibility gate before ever rendering**, unconditionally. Flagged/self-excluded/unknown-protection-state sessions see no "top picks" nudge, full stop.
- Surfaced only as a passive "top picks" card (mentor's mascot framing), never inserted into or blocking the bet-slip/confirm flow, never worded with urgency.
- No location/personal-data enrichment (§5) — this is itself a compliance-by-design point, not just a data-availability limitation, and should be stated as a deliberate choice in the compliance note (once written — Phase E).

## 8. Open questions / stated assumptions / production dependencies

1. **`EPS_Offers` → live event log join is confirmed impossible in-sample** (§3.4) — production would need FEG's internal `fixture_id`-to-name mapping. State this plainly to the mentor; don't claim it's wired.
2. **`sport_name` normalization** (casing/language) needed before any sport-level aggregation or reporting.
3. **`betslip_placed` vs `betslip_placed_bet` grain** must be handled correctly everywhere — conversions are counted by distinct `betslip_number`, not by row count. Confirmed already done correctly in our earlier funnel analysis.
4. **Personalization via `SB_Player.csv` only applies to known `PlayerID`s** — don't let it leak into the anonymous-session cold-start story; keep the two cases (known vs. anonymous) explicitly separate in both the code and the pitch.
5. **Context-slicing in the offline aggregation should stay moderate** (a small number of dimensions) — over-slicing produces sparse, unreliable counts; that's precisely where the lightweight ranking model (§6.3) is the right tool, not more slicing.
6. **`README.md` and all four required `docs/` files do not exist yet in this project** — write them fresh against this pivot before submission; do not adapt any pre-pivot draft that assumed the four-branch casino-inclusive framing.
7. **The Phase X cross-dataset bridge (fixture_id ↔ human-readable names via PlayerID+date correlation) is a real, promising signal but not a solved mapping** — see §10. Do not treat it as production-ready odds/name enrichment until a per-leg matching strategy is verified.
